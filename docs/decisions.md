## Standing rules, applied 2026-11-10

- The plugin stands alone. It depends on no other plugin; other plugins reach it only through optional adapters.
- Public since 2026-11-10.
- No family tags yet: `compliance` (a draft family name) removed from the keywords before the first publish; the categories stay `security` and `privacy`.

- 2026-11-10: `adoptExistingEntries`, as the first site asked for its switch. One adoption seal in the seal chain covers every unhashed entry by content (not values), so pre-chain history is tamper-evident from the cutover on. Unhashed entries after it are breaks. Adoption is allowed after regular seals (the site's seal job may run before the script), but refused once the trail has been pruned. Built on branch `adopt-existing`, merging after its security read, so the owner's first publish includes it.

- 2026-11-10 (self-audit): in `onWriteError: 'log'` mode the entry is written through the database adapter, so a failed entry never undoes the change it records; `fail` mode keeps Payload's validation and undoes the change, as before.

- 2026-11-11 (fixes for the site wiring and the combo test; revised after the security read of ef35392): **`fromPluginEvent` stays strict except for a failed write with no `req`.** ADR 0001 decision 6 and Must 2 of the pre-publish read stand: a mapper that throws, an unknown action or origin, or no Payload to be found throws with or without a `req`. A failed write throws when the event has a `req`, so a plugin awaiting `onEvent` in its transaction is undone. Only a failed write with no `req` (MFA's `start(payload, { userId })`) logs the error's name, never its message, and returns: the plugin has already saved its state, there's nothing to undo, and rejecting only broke its call. `onError: 'fail'` throws always, `onError: 'log'` never.
- 2026-11-11: an event with no `req` and no `payload` uses `{ payload }` bound to `fromPluginEvent`, else the one Payload the plugin started on in the process (registered in `onInit`, forgotten on `destroy`). With several running it refuses rather than guess which site's trail to write. Payload's hot reload reuses its instance and doesn't rerun `onInit`, so a dev server doesn't grow the list.
- 2026-11-11 (security read of ef35392): **changes the saved copy can't show are decided from the database.** For fields that are hidden or read-restricted, and for the hash and salt, the plugin reads the record inside the write's transaction before it (`beforeChange`, or `beforeOperation` for a restore, whose `beforeChange` gets a copy of `req`) and after it (`afterChange`), and keeps only digests. A field counts when its stored digest changed, and `password` when the hash or salt did; the caller's data plays no part. Per-write state lives in a `WeakMap` keyed by `req`, one stack frame per operation, never in `req.context`, which a caller can share between concurrent writes (from the first site's audit, PR #117).
- 2026-11-11: **a reset by emailed link is recorded from `afterLogin`, not `afterOperation`.** The first site's review preferred `afterOperation` on `resetPassword`, inside the reset's transaction if Payload gives one. It doesn't: Payload commits before `afterOperation`, so an entry written there could fail after the password had already changed. `afterLogin` runs inside the reset's transaction, after the write. It's tied to the reset's own account (found in `beforeValidate`) and its success (the stored hash moved), so a failed reset, or a plain sign-in afterwards, records nothing.
- 2026-11-11 (re-read of 4fbe939): **before-write readings are keyed by request and record, and a missing one fails closed.** Each write adds its own reading under `collection:id` and takes its own back, so several writes at once on one request (a hook fanning out updates) can't drop each other's; creates need none. If an update reaches `afterChange` with no reading from before, or the reading after can't be made, the plugin doesn't fall back to the saved copies: it throws, which undoes the change, as ADR 0001 decision 3 does for an entry that can't be written. With `onWriteError: 'log'` the change goes through, an error is logged, and the entry lists what the copies show. Marking the watched fields "unknown" in the entry was the other choice; it was left out because an entry would then name fields that may not have changed.
- 2026-11-11: a reset's account is found by its link in `beforeOperation`, inside the reset's transaction, replacing the `beforeValidate` hook (a nested write in a site hook could have been taken for it). `afterLogin` records only for that account, and clears the state, so a second sign-in on the same request records nothing.
- 2026-11-11: **verify streams.** `verifyAuditTrail` reads entries, heads and seals a page at a time (`pageSize`, default 1,000; a page plus the row it starts from is the most it holds) and keeps only running state: the entry before, the chains finished since the heads were last read, a seal's running digest. Its signature and its answers are unchanged; the old function is kept in `test/legacy-verify.ts` as the reference the tests compare against.
  - **Order comes from the database, never from JavaScript.** Chains and heads are read in the same database order and matched side by side, so a site's collation can't make the two disagree. A head break waits until every entry is read, since the old verify reported entry breaks first.
  - **Fails closed.** A read that throws, returns more than its limit, doesn't start at the row the last page ended on, or brings a chain round again is a failed result with the place and `finished: false`. A read error is reported by name, never its message. It used to throw; a result was chosen so a job that only checks `ok` can't mistake it for a pass.
  - **`from` takes a digest, not an id or a date:** it's what `onSeal` hands out, so it's what a site has kept outside the database. The seal is recomputed from its own entries before anything is trusted from it, because its `upTo` is in the digest: moving it later to hide entries is a break. From a checkpoint, the seals written before it that end after its cut are recomputed too. An adoption seal is refused. An entry may start mid-chain if the one before it is dated at or before the seal; that earlier entry isn't read.
  - **A partial check says so.** `partial`, `finished`, `range` (`from`, `skipped`, `read`) and `summary` are always present. Positions in the summary count entries in time order, with the skipped ones counted by the database. `stopAfter` gives `ok: false, finished: false` and no break. There's no cursor to resume a stopped run from: resuming is from a seal, which can be verified, not from a position the caller hands back.
  - **A compound index on `chainKey`, `seq`** was added for the paging sort. Seal ranges sort by `at` alone (indexed) and order ties by id afterwards, so no page needs a blocking sort.
  - Left as it was: `since`, `sealAuditTrail` (reads one interval at once) and `adoptExistingEntries` (reads the whole old log).
- 2026-11-11 (second pass): **a checkpoint pins the seals it cuts away.** Two prunes left a seal whose predecessor was deleted next to an older checkpoint, and verify reported a link break on an intact trail. Verify also took the first seal it read on trust, so the oldest seal could be removed with its entries unseen.
  - Prune now puts in the checkpoint, and in its digest, the digest of every seal the cut removes that a seal left behind links to (`pins`; the checkpoint's own link and a departing adoption seal's included). It's computed inside the checkpoint's transaction.
  - Verify accepts a seal that doesn't link to the one read before it only if a checkpoint at or after it pins the digest it links to. Only a seal with no link at all may be the first, and only when nothing comes before it. The seal a `from` check starts at is taken as given, since the caller vouches for its digest.
  - Pins count only on checkpoints (an ordinary seal's digest doesn't cover the field), and only from a checkpoint the same check reads and recomputes.
  - Not chosen: deleting older checkpoints at each prune (a kept adoption seal would still dangle), and trusting a seal's `fromAt` (its digest doesn't cover it).
  - A checkpoint from before this change has no pins, so a trail pruned by an earlier build reports a link break. Nothing was published with the old format and no site runs it, so there's no migration.
- 2026-11-11: **the paging index is declared, not created.** `chainKey, seq` is in the trail collection's `indexes`; the plugin never creates an index itself. A site that builds indexes by script gets it from the collection config. Verify gives the same answers without it (tested with the index dropped), only slower.
- 2026-11-11 (after the security read of 8a3bebb; approved with three shoulds and a nit, all taken):
  - **A seal head with no seals is a break.** With the head removed as well, the database holds no sign there were seals, so a full verify passes: that's a stated limit, and the README tells sites to keep `onSeal`'s digest elsewhere and check `from` it.
  - **From a checkpoint, every seal is read.** Starting part-way left a surviving seal that links to an older checkpoint looking unlinked. Before a cut there are only older checkpoints and seals still in range, so reading them all costs little, and the link rule is then the full verify's. From an ordinary seal, reading still starts at that seal.
  - **Verify names each cut.** `cuts` (seq, digest, upTo, pins, and the database's unprotected `createdAt` as `written`) and a line in `summary`. A forged checkpoint appended with the seal head moved can't be told from a real one inside the database; the owner's own record of prunes can tell.
  - **Prune verifies first, by default.** A full verify, not one of the range alone: the range to be cut is the oldest part, whose chains and seals lead into the rest. It refuses on a break or an unfinished check, before clearing values or deleting anything. `verify: false` is the way out. Clearing values alone doesn't check: it cuts nothing.
